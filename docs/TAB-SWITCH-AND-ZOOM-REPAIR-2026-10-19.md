# Reader tab switching and zoom repaint — 19 October 2026

## Changes

- Restoring an already-open PDF now uses its open PDFium source and authoritative in-memory annotations. It does not reopen the PDF, parse the annotation sidecar, reapply unchanged imported-annotation suppression, queue a redundant first-page annotation job, animate page entrances, or first fit/lay out page 1 before restoring the saved page. Failed activation restores the previous tab's moved annotation data and layout.
- A parked tab transfers its `AnnotationStore` vector instead of copying all marks out and reinserting them with an ID lookup for every mark (formerly quadratic). Unchanged sidecars are not rewritten on a switch; failed saves remain dirty and will retry. Previously opened recents update in memory on the tab input path, and the small recent-list file is flushed after the first presented frame (and again on orderly shutdown if needed).
- Each parked tab may transfer its already calculated page rectangles into a lightweight layout snapshot, which is valid only for the same viewport dimensions, scale, layout, grid size, rotation, page count and PDF geometry revision. A valid restore makes **no per-page PDF metadata calls**. Changed geometry or viewport triggers a correct new layout. These are page rectangles, not page bitmaps (approximately 24 bytes per page with this compiler); the existing <=384×576 actual-viewport preview and inactive-raster release remain in place.
- After zoom or panel-driven Fit width motion, the frame scheduler now notices when the displayed raster scale differs from the finished zoom scale. It schedules a final full stage frame without any click; that frame requests the final-scale PDFium tiles. The existing worker completion wake/poll path then triggers another full repaint as tiles arrive. Once settled, no repeating idle repaint is requested.

## Evidence and limits

Linux headless UI checks, then PDFium+Skia build and **19/19 CTest** pass; added checks cover final zoom-scale scheduling, panel-fit settlement, preserving a 12,000-annotation store by move, and restoring 6,000 pages without new PDF metadata calls (and rejecting stale geometry after resize). Android `assembleDebug` and `lintDebug` passed for the matching application source. A later attempted rebuild for an optional cache adjustment failed when its Gradle daemon disappeared; that adjustment was reverted, so the delivered APK is the successfully built version, not an unbuilt later source change. No Android emulator/phone or Windows GUI was available. This is a code/test improvement, **not** a measured zero-millisecond guarantee on a target device: input dispatch, the bounded <=384×576 GPU scene readback on tab exit, occasional unsuccessful annotation-save retries, and first paints still occupy some UI-thread time. PDF tile rasterization and PDF text extraction themselves run on PDFium workers; completed pixels can only become visible after an actual frame. Testing large real files on target hardware is still needed to measure worst-case latency and GPU stalls.
