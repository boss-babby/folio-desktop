# Mobile PDF rendering and touch pass (historical)

**Historical build only:** the APK path/hash and build verification below describe the previous, superseded APK, which has been removed. For the current corrected build and its limitations, see `ANDROID-URGENT-REGRESSION-FIX.md`.

This pass responds to five phone screenshots supplied by the user. The screenshots show (1–2) a rectangular grey region behind a text-selection popup/colour palette, (3–5) pages appearing progressively in white tiles, clipped page content at zoom, a page counter truncated on a phone, and a black top system-bar region without readable time/icons. Images alone do not establish device CPU, memory or the exact PDF rendering time.

## Root causes and implemented changes

1. **Popup rectangle:** `FolioApp::paint` could choose a *chrome-only* retained repaint for a popover covering the document. It filled the damage area with the UI background while `Widget::paintTree` skipped the document canvas, leaving a background-coloured hole. Partial paint is now restricted to damage that does not intersect the stage; popovers over the document repaint the page underneath. Title-bar-only hover still uses partial damage. The retained-scene test checks popup open/close and chrome hover separately.
2. **Progressive white tiles:** The first viewport previously queued only high-resolution 512-device-pixel tiles. On a cold page there was no whole-page image to show while those requests completed. `PdfiumPageSource` now requests one low-resolution **visible-page preview** before its tiles; the worker prioritises this particular job over tiles, then returns to visible tiles. The actual PDF page dimensions are checked on the PDFium thread before rasterising the preview, because newly opened documents temporarily advertise page-one geometry for later pages. The preview is at most 512 × 768 BGRA pixels (~1.5 MiB) plus normal Skia/GPU image copies, not an unbounded full-page raster. The existing visible tile size remains 512 device pixels and the existing 24 MiB Android / 48 MiB desktop source budgets remain soft for oversized visible viewports. No speculative offscreen prefetch was added. A cold-page test checks that the bounded preview appears while tiles are still filling.
3. **Drawing changes pages:** An armed annotation tool now owns one finger until release instead of falling through to pan if the stroke leaves the page. Samples are mapped to and clamped within the page where the stroke began; entering a neighbouring page cannot transplant the mark. An interruption cancels an uncommitted draft; long-press text selection is disabled while an annotation tool is armed. Pinch/two-finger pan remain available and cancel a draft when a second finger lands. The mobile-input regression covers touch stroke/interrupt, earlier tap-versus-scroll behaviour and pinch centring. Stylus/mouse cancel also discards an unfinished draft.
4. **Black top / hidden clock:** The Android manifest no longer selects a fullscreen activity theme. `FolioActivity` makes the native system status/navigation bars visible, sets their background to Folio's light/dark UI background and selects contrasting system icons. Native shell updates the bars when the app theme changes; Java reapplies them on resume. Android, not Folio, draws the actual clock, battery, notifications and system gesture bar. This requires on-device validation across OEM skins, display cutouts and gesture-navigation variants.
5. **Phone page counter:** Compact view removes whitespace around the slash and gives the field 58 rather than 46 logical pixels so multi-digit page counts are less likely to ellipsise.

## Tradeoffs and what is not proven

- The first preview adds up to ~1.5 MiB in the PDFium source plus a copied Skia/GPU image; it is usually a better experience than white gaps, but on an extremely complex page a whole-page low-resolution PDFium render can still take time and briefly precede the first sharp tile. It is not a benchmarked speedup on the user's PDFs.
- A popover crossing the document takes a full retained-scene repaint while it animates. This avoids corrupting the retained PDF but may cost GPU time during the short popup transition. Stationary top-toolbar hover still follows the earlier chrome-only path.
- The touch tests are headless Linux regression checks. No actual Android device or Windows GUI runtime is present here; absence of further OEM-specific input bugs, Android status-bar correctness, PDFium throughput and RSS changes cannot be certified from compilation/tests.

## Device acceptance checklist

On a real phone, reopen the three PDFs in the screenshots and check: repeated selection popup open/close and palette swatches with no rectangular remnants; first paint, scroll, zoom and tab switch with a readable full-page proxy before sharp tiles (no sustained white holes); a one-finger ink/highlight stroke crossing a page edge does not scroll or move pages, a two-finger pinch still works, and interruption leaves no mark; page count is readable for documents with hundreds of pages; clock/battery/icons are visible in both light and dark app themes and after app resume/rotation. Record device model, Android version, DPR, PDF page complexity, frame time and process-memory figures before claiming a measured performance gain.
