# Workspace cleanup, native file handling and Windows workflow

## Location and activation

The requested workflow file is [`github-workflows/windows-clang.yml`](../github-workflows/windows-clang.yml). The earlier untracked duplicate in `.github/workflows/` has been removed. GitHub Actions **cannot execute a workflow from `github-workflows/`**; to run it, copy this template to `.github/workflows/windows-clang.yml` in your GitHub repository and push it together with the source changes. Instructions: [`github-workflows/README.md`](../github-workflows/README.md). Historical note: the MSVC release workflow used to be tracked in `.github/workflows/`. The current clean-build template is now kept only under `github-workflows/`, as requested; GitHub needs an explicit copy in the remote repository to activate it. See `BUILD-WINDOWS.md`.

**User-provided GitHub Actions result:** the Windows ClangCL application compiled, then CTest passed 13/14 tests. Only `engine.pdfium` failed: at page 1, 2× scale, bleed 48, 42 image subpixels differed by a maximum of **1/255**. This is PDFium coverage-rounding variation, not a visibly broken tile seam. The original test incorrectly required exact equality at 2×; that condition has been narrowed to 1×. At 2× and above the test now requires a maximum delta of 1/255 **and** at most 256 differing subpixels; larger/visible seams still fail. Linux PDFium regression tests pass after this change. A new GitHub run is required to check Windows: its full tests and packaged executable have **not yet passed together**.

The earlier workflow stopped at the failed test, so it never uploaded a zip; that runner's build cannot be retrieved after the job ended. The updated workflow **still fails** on test errors but packages and uploads the compiled app as `Folio-windows-clang-x64-UNVERIFIED` (with `LastTest.log`) after a failed test or smoke check. A fully green run uploads `Folio-windows-clang-x64`. The separate MSVC release workflow has the same safeguard and never publishes a failed build as a GitHub Release. Copy the changed template to the repository's `.github/workflows/` before rerunning; the file in `github-workflows/` alone will not execute.

## Application corrections in this pass

- **Native desktop Save As:** Folio now prefers the operating system's Save dialog when available, with an in-app chooser as fallback. On Windows the dialog uses the requested starting folder, a PDF file filter, `.pdf` as default extension and filesystem-only results. It runs on the UI thread as a modal dialog; PDF writing remains asynchronous.
- **Desktop without PoDoFo:** Save As uses the PDFium worker to prepare a separate annotated PDF in the destination directory, then performs a fast rename. It never modifies the open original, refuses existing destination files rather than overwriting them, and preserves in-session marks on failure. Highlight, underline, strikeout, ink, note, box and ellipse are supported; free text/stamps/signatures fail visibly. A missing reader-level Save As test source file was restored and now runs.
- **Windows dependency/bootstrap:** the `chromium/7568` PDFium and `m144-e2e6623374-4` Skia archives have SHA-256 pins, and the bootstrap expects their actual import-library/DLL and `Release-windows-x64` paths. PoDoFo is OFF for the Windows workflow; requesting it ON without a library fails configure rather than silently dropping support.
- **Scope:** in-place incremental Save and page-tree editing remain PoDoFo-only. This pass does not provide durable recovery of unsaved in-session edits, Windows Unicode PDFium path coverage, or proof of Windows GUI/device behaviour. Existing Android code and the retained APK were not rebuilt in this pass.
