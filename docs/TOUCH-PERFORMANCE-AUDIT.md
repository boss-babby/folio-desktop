# Folio touch, inspector and memory audit

**Date:** 10 October 2026. This report covers the follow-up to the first mobile build. **Live 390×844 UI preview:** https://8080-imeflobe8ir488xbnmj59.e2b.app/ (open via the Arena preview card; the direct link may require Arena's traffic-access token). This Linux stream runs the shared C++/Skia UI, **not** an Android runtime. Device RAM and thermals have not been measured here.

## Root causes and changes

| Symptom | Root cause in code | Fix |
|---|---|---|
| Pinch drifts away from the fingers, or shifts sideways | `GestureTracker::onPointer` computed the previous midpoint from each finger's *previous event*. Android sends one event per pointer, so alternating moves counted the other finger's travel twice. `PageStage::handleTouch` then applied an old zoom anchor before it had re-laid out the pages. | Calculate the midpoint from both current positions **before** updating the moving finger. For a scale change, capture the PDF coordinate under the old midpoint, relayout at the new scale, and position that PDF coordinate under the new midpoint. Pure two-finger panning does not trigger layout. Suppress accidental taps/flings on pinch release. |
| Narrower pages appear offset while scrolling a mixed-size document | Continuous layout centred each page against the viewport instead of a common document width. | Centre all continuous-reading pages in a single width determined by the widest page. Reset horizontal scroll when content fits the viewport. Reset stale geometry and anchors when changing documents. |
| Right-bottom tool inspector cannot show all controls | The inspector's 24 swatches, size, opacity and layout controls were fixed directly in a sheet shorter than their total height. | Give the inspector a clipped, touch- and wheel-scrollable `ScrollView`. Keep its close button and title stationary. Move body controls and custom swatch/header paint into scrolling content; keep content height in sync with the selected tool. |
| Inspector opening and repeated scrolling lag | `ReaderScreen::onPaint` re-laid out the whole reader including the swatch grid and rewrote the page label **on every frame**. It also applied per-button alpha layers during a sheet transition. | Layout only while panel/focus geometry is animating (plus its final frame), and on ordinary layout invalidation. Rely on the page-changed event for the label. Apply one alpha layer to the inspector scroll container. Explicitly update the document name on open. |
| Phone RAM rises and zoom/repaint stutters | PDFium pages, Skia bitmap wrappers, optional vector-page rasters, GPU resources and PDFium open pages have **separate** budgets; several were 192–256 MiB each. A capped single layer did not cap the process. The native CPU fallback also free-ran the paint loop while work was pending. | Android limits: PDFium resident pages **32 MiB**, PDF raster longest edge **2048 px**, SkImage wrapper copies **32 MiB**, vector raster cache **16 MiB**, Ganesh GPU resources **32 MiB**, PDFium open pages **4**. Desktop retains larger but reduced budgets: respectively **96 MiB**, **4096 px**, **128 MiB**, **128 MiB**, **128 MiB**, **12 pages**. Android native animation loop targets ~45 Hz instead of a zero-timeout busy loop, while input can still wake immediately. Android CMake builds use a one-compile-at-a-time job pool to avoid OOM on small builders. |

These are **independent upper bounds**, not a promise of total-process RSS. Each may temporarily coexist with the source PDF bytes, PDFium's internal allocations, text extraction, the framebuffers and the Android runtime. Opening a huge PDF still loads the entire file into memory in `PdfiumPageSource::open`; a streaming/memory-mapped reader would be required for a strict whole-process RAM ceiling.

## Checks performed

- Linux Ninja build succeeded with the new code; `ctest --test-dir build --output-on-failure -j 2` passed **13/13**. The mobile-input regression test now checks alternating-finger centroid deltas, preserving the PDF coordinate at a moving pinch midpoint, clearing horizontal offset when the page fits, and centring differently sized pages on one document axis.
- Exercised the 390×844 Linux stream with a real bundled PDF: opened the right-bottom sheet, selected the Pen tool, and dragged within its swatches to reveal Width, Opacity and Layout; see [inspector at top](inspector-ink-top.jpg) and [inspector after scroll](inspector-ink-scrolled.jpg). A simulated two-finger zoom produced the [pinch screenshot](pinch-anchor-preview.jpg). These visual checks are not Android hardware validation.
- In that *Linux stream* session at 390×844 after the pinch, the `/stats` endpoint reported about 4–5 ms render time with the inspector up and approximately 25 MiB of Skia image wrappers after several zoom scales; Linux stream process RSS was about 74 MiB at that point. Its DPR is 1 and it has no phone GPU/Java process, so **none of these numbers predicts Android RAM or FPS**.
- **Updated Android APK built successfully** with `tools/build-apk.sh Debug`: both `arm64-v8a` and `x86_64` native libraries packaged, Gradle `assembleDebug` and `lintDebug` succeeded with **no lint issues**. That APK was superseded and removed during cleanup; the latest prior APK is `/home/user/folio-android-parity-debug.apk`. The earlier APK was signed (APK v2 verification passed), includes `classes.dex` and both PDFium libraries, exports `ANativeActivity_onCreate` and the JNI keyboard callback. No Android device/emulator ran the APK.

## Still required before calling mobile performance complete

1. On-device arm64 profiling with `dumpsys meminfo`, Android Studio heap/native allocation trace and Perfetto frame timeline during long-PDF opening, prolonged scrolling/pinch, repeated inspector opening, background/foreground and low-memory conditions. Record PSS peak, steady-state PSS, 95th/99th percentile frame time and thermal throttling. The sandbox has no Android device/emulator, so this acceptance gate remains open.
2. Replace whole-file PDF loading with a file-backed or mapped PDFium source to avoid a duplicate full-document RAM copy; cap text extraction, PDFium page allocations and queued render results; implement trim-on-background/low-memory.
3. Test both low-end and high-DPR devices. A 2048-pixel page cap can look soft when zoomed deeply; if so, replace full-page bitmaps with visible tiles rather than raising a global cache limit indiscriminately.
4. Confirm touch-slop, pinch anchoring, keyboard focus, inspector swatch-tap versus drag, and scroll-edge behavior on actual hardware; the streaming browser's event cadence differs from Android's batched MotionEvents.

The previous audit `MOBILE-AUDIT.md` describes broader remaining features such as Android Save/export and persistence; those are **not** made complete by this performance pass.
