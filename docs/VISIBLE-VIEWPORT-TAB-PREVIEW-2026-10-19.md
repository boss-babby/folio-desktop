# Reader tab-switch viewport previews — 19 October 2026

## Problem and root cause

A parsed PDFium document in RAM does not mean its decoded image is in RAM. On tab exit Folio previously kept an *already existing* <=512×768 raster of the current **whole page**, if available; it dropped the viewport's high-resolution tiles. A fifth or older parked tab lost even that proxy. On tab re-entry `ReaderScreen::loadPath` reloaded the sidecar and invoked `syncImportedSuppression`; `PdfiumPageSource::suppressSourceAnnotations` then **unconditionally called `suspendVisualCaches()`**, despite `PdfiumWorker::setSuppressed` returning early internally when nothing changed. Thus the page preview often vanished before the first return frame. `FolioApp` also purges copied Skia images on document change; that is necessary to control GPU/CPU copies and is not a disk-backed page cache.

## Implemented

- A no-change imported-annotation suppression update now returns false from the worker and **does not** discard existing visual pixels. A *real* change still invalidates pixels/metadata so edited imported marks cannot paint with an old PDF base. A PDFium-backed test checks both outcomes.
- On a native tab exit, the shell captures the **already presented reader canvas viewport rectangle** (including the visible arrangement of pages, their clipped portions, margin, theme and Folio marks), not page 1, not the entire last page, and not the whole application window. It downsamples to at most **384×576 BGRA pixels = 884,736 bytes = 0.844 MiB** per inactive PDF. For 12 tabs the upper bound on these **stored raw previews** is about **10.1 MiB**; size is often smaller. That is a budget estimate, not an Android RSS measurement. A GPU scene is downscaled into a small GPU surface **before** the readback; the software scene is sampled directly. Capture happens only on a switch, not each frame. If capture cannot be performed (missing context/background/headless), the older bounded page-preview mechanism remains the fallback.
- When a viewport snapshot exists, that inactive source drops all decoded page rasters and text. It retains the PDFium document/worker for the existing fast tab switch. The saved `PageStage::ViewState` restores the same page, layout, X/Y scroll and zoom; a bounded snapshot fills only the canvas while current-viewport pixels render asynchronously. The source reports whether *every canvas-visible tile/page* is ready. On the first complete sharp frame, the snapshot image key is invalidated and its CPU bytes released; an unrenderable page has a ten-second escape so an old screenshot cannot cover an error forever. Tool HUD/scrollbars paint over the temporary snapshot. On user-initiated navigation/zoom, the snapshot is discarded rather than incorrectly covering a different viewport.
- Snapshots are owned only by inactive tab records or briefly by the returning stage; closing tabs removes them. Minimise/background explicitly drops inactive snapshots as part of the existing memory-release path. Neither an entire PDF nor every page is cached on disk, and there is no promise to retain a full-resolution first/last page.

## Boundaries and evidence

The GPU/Skia image cache, live GPU scene, PDFium native document/mapping, worker thread and allocator have separate memory costs. The **0.844 MiB** figure is the maximum stored viewport bitmap, *not* the total per-tab RSS or a measured 12-PDF process total. Tab return may still briefly show a downsampled, slightly blurred snapshot until final-scale PDF tiles are ready; a page that was never drawn before the tab exit cannot be recreated by any snapshot. Resize/theme changes or navigating to another viewport invalidate/replace the old scene as appropriate. Minimise deliberately drops inactive snapshots, trading a possible re-render after a memory-pressure event for lower background memory.
