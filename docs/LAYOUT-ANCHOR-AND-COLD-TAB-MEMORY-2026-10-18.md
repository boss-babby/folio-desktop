# Layout anchoring and whole-app memory review — 18 October 2026

## Changes in this revision

- `PageStage::setLayout` now carries the **selected page and its on-page X/Y reading position** into Continuous, Two-up, Grid, and Single layouts. It translates the old scroll position into the new geometry instead of reusing layout-specific absolute scroll coordinates, centres a selected right-hand spread page horizontally, cancels stale scroll momentum, and skips the new-document entrance animation. The fit animation keeps the selected page anchored as scale changes. `updateCurrentFromScroll` does not immediately relabel a focused right-hand spread page/grid cell as the first cell in that row.
- A 24-page mixed portrait/landscape regression starts on page 18 and checks Single → Continuous → Two-up → Grid → Continuous → Single, including an actual page-18 hit test and right-page visibility. The focus remains page 18 throughout. The test's scroll threshold is intentionally only a guard against returning to page one: the fit zoom and landscape pages make a hard-coded 8,000-dp expectation invalid.
- Parking/suspending an inactive PDF now also frees **parsed imported-annotation metadata** (`PdfiumPageSource::annotations_`). The Notes/indexing and imported-mark metadata can be requested again on activation; source PDF, saved Folio sidecar and tab view state remain unchanged. A worker-backed regression checks that metadata is released and re-indexed. This specifically addresses one non-raster growth path; it does **not** close inactive PDFium documents.
- Zoom behavior is retained, not replaced: `PageStage::onPaint` freezes `rasterScale_` while zoom/rotation/viewport-width movement is active, stretches already resident pixels at each intermediate geometry, and adopts the final scale once movement stops. The PDFium source also uses an existing preview/old-width tile as a transient proxy until destination-scale tiles arrive. Its worker prioritises visible preview/tiles. Intermediate animation scales are not requested as new PDFium render resolutions by this stage path. Settled pages sharpen asynchronously, not by blocking a drag or making every animation frame a full re-render. A very large/fast jump may momentarily show low-resolution or missing areas if the old viewport never had pixels there; this is not a promise of instant *sharp* pixels.

## Why RAM can remain high without visible old-page renders

This is a **source-level allocation inventory, not measured Android or Windows RSS/PSS**. Rendering is only one part of process memory. Current normal tab switches park an old tab's pixels, but deliberately keep its `PdfiumPageSource`, worker thread, live `FPDF_DOCUMENT` and `FileMappedAccess` mapping for fast reactivation (`ReaderScreen::OpenDoc`, `stashActiveDoc`, `PdfiumWorker::threadMain`). The worker calls `rast.releasePages()` after jobs: not keeping `FPDF_PAGE` handles is different from closing the document. Even a document whose pages are no longer painted can retain PDFium's document object, parsed cross-reference/object/font data, worker stack and bookkeeping, outline, page metadata, suppression state, and file-backed pages touched by the OS. PDFium's internal memory is **not bounded** by Folio's bitmap budgets. `PdfiumWorker::suspendVisualWork` cancels queued raster/text/annotation work but does not close the document or cancel all metadata/outline work; an already running render finishes before its result is discarded by the visual epoch. Thus a just-parked tab may still briefly use CPU and temporary native memory, even if its page is no longer shown.

| Allocation/pool | Actual policy in this checkout | What can still remain |
|---|---|---|

An `open(bytes)` engine path *does* keep a snapshot. | Mapping's virtual size is **not** resident RAM. Touched file-backed pages can appear in RSS and may remain in OS cache, usually reclaimable; PDFium-parsed *private* allocations are additional. Keeping a private imported PDF on disk is not itself duplicating its full bytes in private RAM. |

The first four previews are optional, not guaranteed or eager new renders. Newly fixed: inactive imported-annotation metadata is now cleared as well. |

The image cache is 24 MiB Android / 40 MiB desktop; separate offscreen `drawCached` raster budget is 16 MiB Android / 32 MiB desktop (mostly non-PDF content in the active PDF path). | These are not the source pixels counted above. Cache invalidation on a tab change is applied at the next paint; allocations may not immediately leave the process allocator's committed pages. |

The retained scene deliberately enables partial redraw and should not be discarded on every tab switch. |

A synchronous reopen can also overlap an old source's asynchronous retirement briefly. |

Do **not** add the budgets and label the sum observed RAM: they are independent **limits or soft limits**, not simultaneous use measurements, and they exclude PDFium internals, thread stacks, graphics driver, allocator retention and platform runtime. A newly opened visible PDF still has its own preview/tiles. `mmap` file size is address space, not a guaranteed allocation of the entire file. Windows Working Set, Linux RSS/PSS and Android `dumpsys meminfo` have different accounting. This pass does not have a phone/emulator or Windows GUI to sample those counters.

### Low-memory inactive-tab design (investigated, **not enabled**)

A true cold tab should keep only its path/durable SAF locator, page and `PageStage::ViewState` (layout, zoom, scroll, rotation, viewport), theme/panels and saved annotation identity/revision. After committing edits and atomically saving the Folio sidecar, cancel visual/notes jobs; **defer** closing a worker until its export finishes; retire the `PdfiumPageSource` off the UI thread. Keep one or two most-recent inactive documents warm for instant switches; make older ones cold when a memory-pressure signal arrives or an explicitly enabled low-memory mode is chosen. A cold tab has no PDFium document, mapping, worker, decoded pixels or parsed annotations. Its small record still lives in RAM; sidecar and source PDF are already disk-backed. This is the only approach here that would actually release old PDFium native allocations, rather than merely clearing page bitmaps.

For fast recovery, persist an *optional* small, private, versioned cover/last-page preview with a source fingerprint and page/rotation/theme identity (illustrative compressed size perhaps tens–hundreds of KiB, **not measured**); display it stretched to the restored viewport while the source opens asynchronously and destination-scale visible tiles replace it. Reopen the original PDF from the retained seekable private copy or durable SAF grant: do not serialize PDFium pointers, raw mappings or full-resolution tile grids. Bound disk size/LRU, clean on document removal, verify identity before reuse, and treat previews as potentially sensitive user data. Recheck file fingerprint, grant, and annotation revision; if a linked source is gone, keep its tab state and saved annotations/sidecar, surface a recover/relink action instead of silently losing them. Keep copy remains the safe default. An in-flight Save As/share needs its source until completion; a cold transition must never discard unsaved changes.

**Why this is a proposal, not silently shipped:** current `loadPath` synchronously waits for non-prepared opens and reconstructs notes/annotations; simply setting `OpenDoc::source=nullptr` would make switching old tabs block the UI and risks stale imported-mark suppression, lost callbacks, revoked SAF access or export races. A correct cold path needs async reopen and restore tests, memory-pressure/permission tests, and real PSS/latency comparisons before changing the default instant tab-switch behavior. No rendered-page disk cache has been added in this revision.

## How to verify memory and responsiveness on a device

Use the *same files* and window/DPR in a repeatable series: process start/Home; open PDF A, first preview, settled sharp page, 3 seconds idle; open PDFs B–E without reading A; switch back; zoom/pinch repeatedly; minimise/restore. On Android collect `adb shell dumpsys meminfo <package>` (TOTAL PSS, Private Dirty, Graphics, Java/Native Heap, mmap), optionally `adb shell cat /proc/<pid>/smaps_rollup` if permitted, and Perfetto allocation/frame traces; mark each sample with the active/parked/cold state and source sizes. On Linux use `/proc/<pid>/smaps_rollup` and heap/graphics counters; on Windows measure Private Bytes, Working Set and GPU dedicated/shared allocations. Record first-preview and final-sharp latency, peak PSS and settled PSS, tab-return latency and whether an inactive source was still open. Compare warm and proposed cold modes only after they have the same permissions/edit-safety behavior. A drop in available free system RAM or an unchanged process working set by itself is not proof that freed source pixels remain live.
