# Real PDFs, navigation, and memory pass

## What changed

- The library starts empty instead of inventing recent documents. Successfully opened filesystem PDFs are written to a bounded (20-item) history file in a per-user state directory: `%LOCALAPPDATA%/Folio` on Windows, `$XDG_STATE_HOME/folio` or `~/.local/state/folio` on Linux, and the NativeActivity internal files directory on Android. Missing files are excluded at startup. Recent cards reopen the actual path and resume the saved page. Switching/closing tabs and returning to the library persist page progress.
- Android's document picker streams provider data into a private **files** directory, not its evictable cache. Reimports of the same content URI use the same hashed directory. Its display name becomes a sanitized filename. The old export bridge now validates its staging path against the private files directory. Existing APKs predate these changes; rebuild the APK before testing them.
- Desktop file opens use a read-only OS-mapped PDFium `FPDF_FILEACCESS` rather than copying the entire PDF into a private in-memory snapshot. Snapshot-backed edits/tests remain supported. Closing the last tab releases the page source, mapped file, and worker; leaving or replacing a document also purges copied Skia images on the next paint. The decoded PDF page cache targets 24 MiB on Android and 48 MiB on desktop (one oversized page, or one raster per nearby visible page, may temporarily exceed its budget); Skia bitmap and GPU-resource budgets were reduced separately. Text extraction for search is incremental rather than queueing every page at once, and no longer retains every processed page's full glyph array. GPU compositing is used where the existing backend supports it; **PDFium page rasterization remains CPU-bound**.
- Evicting a page bitmap now invalidates the associated render-request marker so revisiting at the same zoom schedules a new raster. Failed high-resolution renders retry at lower resolution instead of leaving a white page. Maximum-zoom/equal-zoom revisit have a real-PDF headless regression test.
- Switching **Pages** / **Outline** relayouts the expanded left panel immediately. The inspector defaults to closed. Desktop window controls remain accessible in narrow windows, and the narrow title layout reserves space for them. The text-selection action popup remains open while its markup color palette is opened and while a color is chosen; outside clicks or Escape/deselection dismiss it.

## Correction: Windows CMD console, true partial redraw, and zoom thrash

The user's “command panel” report was **not** about the app's inspector. It was a *separate Windows CMD console window*. The previous reply misidentified it. `folio-desktop` is now built with CMake's `WIN32` GUI-subsystem flag on Windows, and `wWinMain` converts the Unicode command line to UTF-8 before calling the normal native shell. `--help` avoids a modal message box on CI. The `github-workflows/windows-clang.yml` package step checks the actual executable's PE subsystem is **2 (Windows GUI)** rather than **3 (console)**, failing if a console build regresses.

The previous “no hover redraw” fix was insufficient: every *changed* hover still repainted the full window. Native rendering now paints into a **persistent Skia GPU scene surface** and presents its snapshot into the discardable WGL swap buffer. A safe chrome-only frame clips to the union of old/new widget damage, excludes `PageStage` from the paint traversal, and reuses its previously composited PDF pixels. Resizes, document results, scrolling, zoom, theme/screen transitions and panel/layout movement force a full repaint. Software raster rendering uses the same retained/partial path; streaming uses its existing full repaint path. This is a *partial redraw*, not a claim that WGL supports DXGI `Present1` dirty rectangles: a full, already-composited GPU texture must still be presented after `SwapBuffers`.

The high-zoom flash was not just an insufficient cache size. The source cache was keyed by `(page, pixel width)` while its **pending request marker and worker queue were keyed only by page**. A thumbnail and the main PDF canvas repeatedly superseded each other's render at different scales. Both pending state and render queue are now keyed by `(page, requested pixel width)`, and incoming canvas zoom scales supersede obsolete *queued* canvas jobs without suppressing thumbnail jobs. The UI retains one bitmap per nearby page as a zoom proxy; late distant results are discarded. Headless regression alternates a 120-px thumbnail with a >4,000-px page over many draws and checks neither goes blank nor causes repeated raster allocations.

The attached VOSStudio audit informed these choices: serialize PDFium per document, prioritize visible work, retain an old-scale proxy, cancel superseded queued work, and separate chrome redraw from PDF canvas redraw. VOSStudio additionally rasterizes **viewport tiles (512×512)** and presents dirty rectangles through DXGI. Folio still renders bounded whole-page rasters (up to a 4,096-pixel long edge on desktop); copying its tile architecture requires a separate viewport-aware render/cache change and should not be claimed as completed here. Nor should its Library-screen Wine FPS figures be cited as PDF-reader benchmarks.

Validation here: full Linux PDFium+Skia desktop build and **17/17 CTest suites pass**, including a retained-surface hover/canvas test and high-zoom thumbnail/main-canvas regression. `git diff --check` passes; workspace remains under 125 MB after cleanup. No native Windows execution or WGL driver performance benchmark is available in this sandbox. The earlier Android APK was not rebuilt after this Windows follow-up.

## Follow-up: viewport tiles and tab-scoped visual memory (current)

The previous paragraph saying Folio **still** uses whole-page canvas rasters is historical. The native `PageStage` now passes each visible page's intersection with the stage viewport to `IPageSource::drawVisiblePage`. `PdfiumPageSource` enumerates only intersecting **512-device-pixel tiles** using `TileGrid`, queues them on that document's PDFium thread ahead of thumbnail/text/metadata jobs, and blits each tile in its page-coordinate position. There is **no speculative tile prefetch**. Whole-page rendering remains for the small thumbnail rail and the legacy `drawPage` API/tests, not for the main PDF canvas. A thumbnail or the previous on-screen tile generation serves as a temporary zoom proxy until the new tiles land. Obsolete queued tiles are replaced at each full visible frame; work in progress cannot be pre-empted inside PDFium's synchronous matrix renderer, but its result is discarded if the request is no longer on screen. Each worker keeps one mapped/open `FPDF_DOCUMENT` per tab and closes its only `FPDF_PAGE` after each render, text, or metadata job (and after initial geometry). This saves idle memory at the cost of sometimes re-parsing a page for adjacent tiles.

Switching tabs suspends the previous source's queued work and drops all decoded tiles, thumbnails, text and glyph caches without closing its document. Epoch checks prevent an in-flight old-tab result from repopulating that cache. Skia's copied images are cleared on the next paint. After three seconds without user input, the native shell makes **one** pruning pass over source pixels not used by the last painted frame, clears its duplicate Skia image cache, and best-effort trims the native heap. It then blocks on platform window events; PDFium worker completions call the thread-safe platform wake hook, so the shell need not poll a finished document indefinitely. Windows minimise (`WM_SIZE`), X11 unmap, and Android window teardown release visual caches and the retained GPU scene; restoration rebuilds the scene and visible tiles. On Android, releasing a lost EGL context intentionally does not call GPU resource APIs after `APP_CMD_TERM_WINDOW` unbinds it.
